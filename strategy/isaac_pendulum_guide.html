§ 01 — Install Isaac Lab

One virtual env, one binary path.

Isaac Lab sits on top of Isaac Sim, which is heavy (GB-scale download, CUDA-specific). Follow the official pip-install route inside a virtual environment so the whole system can be nuked and recreated without touching the rest of your setup.

# create a dedicated env (conda shown; uv and venv also work)
conda create -n isaaclab python=3.11
conda activate isaaclab

# CUDA-enabled PyTorch matching your GPU
pip install torch==2.7.0 --index-url https://download.pytorch.org/whl/cu121

# Isaac Sim + Isaac Lab
pip install 'isaacsim[all,extscache]==4.5.0'
pip install isaaclab

# verify — should print version and exit cleanly
python -c "import isaaclab; print(isaaclab.__version__)"

If the verify step fails, the most common cause is a CUDA/PyTorch mismatch. Check nvidia-smi for your driver's max CUDA version and pick a matching PyTorch wheel.

Clone the reference repo (optional but recommended)

git clone https://github.com/isaac-sim/IsaacLab.git ~/code/IsaacLab
cd ~/code/IsaacLab
./isaaclab.sh -h                        # confirms the launcher works

# smoke test: cartpole zero-agent
./isaaclab.sh -p scripts/environments/zero_agent.py \
    --task Isaac-Cartpole-Direct-v0 --num_envs 32

If a viewer window opens with 32 cartpoles rendering at a reasonable frame rate, you're ready to proceed. If it errors on missing nucleus assets, the first run will download ~2 GB of USD files — let it finish.

GPU memory budget. 4096 parallel pendulums is roughly 3–4 GB of VRAM. On a 12 GB card you'll fit easily. On a 6 GB card, drop to 2048 envs. Out-of-memory errors during training are almost always solved by halving num_envs.

§ 05 — Convert URDF to USD

Isaac Sim speaks USD, not URDF.

Isaac Lab's URDF converter preserves inertial properties, joint types, and the dynamics tag. Run it once:

./isaaclab.sh -p scripts/tools/convert_urdf.py \
    source/humanoid_pendulum/humanoid_pendulum/assets/x6_pendulum.urdf \
    source/humanoid_pendulum/humanoid_pendulum/assets/x6_pendulum.usd \
    --merge-joints \
    --fix-base \
    --make-instanceable
--fix-base
Test stand is bolted down; base_link has no 6-DOF floating joint
--make-instanceable
Shared mesh/geometry across parallel envs — critical for memory efficiency at 4096 envs
--merge-joints
Collapses URDF fixed joints into rigid groups (no-op here, always safe)

After conversion, open the USD once in Isaac Sim to confirm:

  • Articulation root is on base_link.
  • pendulum_joint appears as a revolute joint with correct axis.
  • bar_link's inertia tensor matches your URDF values (check Property panel → Physics → Mass).
  • Effort and velocity limits propagated.
Re-convert every time you change the URDF. Isaac Lab caches aggressively — if the USD on disk is stale, sim will happily run with old parameters without warning.
§ 06 — Choose the actuator model

Four options, one right answer for sim-to-real.

Isaac Lab offers four actuator models. Picking the wrong one is the single most common sim-to-real failure. Here's the honest comparison.

Option A
ImplicitActuator
don't start here

PhysX-native PD loop. Very stable, very efficient. But: no torque lag, no velocity-dependent torque curve, and numerical damping added by PhysX is invisible in your model. Policies trained with this rarely transfer cleanly.

Option B
IdealPDActuator
baseline

Explicit discrete PD, effort clipping. No velocity curve. Close to your bench PD, but still idealized — zero torque lag, no F_c. Useful as a sanity check, not the final choice.

Option C
DCMotor
use this

IdealPD + velocity-dependent torque curve matching a DC motor. This is the right model for the X6 — it captures the reality that max torque decreases as speed rises, which matters for policies operating near speed limits.

Option D
DelayedPDActuator
if lag matters

IdealPD with a discrete-step delay buffer simulating communication lag. Use when you want to bake in the EtherCAT latency you measured. Can stack on top of DCMotor behavior manually.

The DCMotor torque-speed curve

DCMotor clips effort according to a linear four-quadrant model:

DCMotor effort clipping $$ \tau_{max}(\dot\theta) = \tau_{sat} \cdot \left(1 - \frac{|\dot\theta|}{\dot\theta_{max}}\right)^+ $$ $$ \tau_{applied} = \text{clamp}(\tau_{commanded},\; -\tau_{max}(\dot\theta),\; +\tau_{max}(\dot\theta)) $$
τ_sat
saturation_effort — peak torque at zero speed (X6: 60 N·m)
τ_max(θ̇)
actually available torque at current speed — linear falloff
θ̇_max
velocity_limit — no-load speed (X6: ~16 rad/s at output)

Below effort_limit (the nominal/continuous rating, 20 N·m for the X6), nothing changes — the policy sees a flat torque ceiling. Above the nominal but within peak, the curve kicks in. This is faithful to real DC motor behavior and prevents policies from learning to ride the peak torque indefinitely.

§ 09 — Observations

Five numbers, chosen carefully.

The observation is what your policy sees at every step. Five things matter for a single-joint pendulum: a continuous angle representation, velocity, previous action, and a time signal.

def _get_observations(self) -> dict:
    theta = self.robot.data.joint_pos[:, 0]          # shape [N_envs]
    theta_dot = self.robot.data.joint_vel[:, 0]

    # Wrap θ to [-π, π] so cos/sin are always defined cleanly
    theta_wrapped = torch.atan2(torch.sin(theta), torch.cos(theta))

    obs = torch.stack([
        torch.cos(theta_wrapped),                          # [-1, 1]
        torch.sin(theta_wrapped),                          # [-1, 1]
        theta_dot / self.cfg.robot_cfg.actuators["x6"].velocity_limit,  # [-1, 1]
        self.prev_action,                                  # [-1, 1]
        self.episode_length_buf.float() / self.max_episode_length,  # [0, 1]
    ], dim=-1)

    return {"policy": obs}

Why these specific choices

  • cos(θ), sin(θ) instead of θ directly Your pendulum is continuous — it rotates past ±π. Feeding raw θ to a policy means the same physical pose (say, 3π and π) becomes different observations, breaking generalization. cos/sin are both continuous and periodic, so the policy sees the same thing at 3π and π.
  • Normalize θ̇ by velocity_limit Neural nets train faster and more stably on inputs roughly in [-1, 1]. Dividing by the known max velocity achieves this without a separate normalization layer.
  • Include previous action Helps the policy learn smooth control (penalize action jumps in the reward — §11). Without prev_action in the obs, the policy has no way to know what it just commanded.
  • Time-in-episode Optional but useful for finite-horizon tasks. Lets the policy learn "end-of-episode" behaviors (e.g., don't wind up angular momentum if there's no time to use it).
Do not include payload mass in observations. Tempting, because you randomize it — but at deploy time, you don't know the real payload. Training with it as an observable creates a silent sim-to-real gap. Either add a mass estimator (from the motor-ID guide's Method 3 RLS) as an upstream node, OR design the policy to be mass-agnostic via randomization alone.
§ 10 — Actions

Torque out, scaled and clipped.

The policy outputs a value in roughly [-1, 1] (PPO uses a tanh-squashed Gaussian). You scale that to a physical torque and hand it to the actuator. Two critical details: the scaling factor and the feedforward-vs-replacement decision.

def _pre_physics_step(self, actions: torch.Tensor):
    # action in [-1, 1] → torque in [-τ_max, τ_max]
    self.prev_action = actions.clone()
    tau_max = self.cfg.robot_cfg.actuators["x6"].effort_limit
    self.torque_cmd = actions.clamp(-1.0, 1.0) * tau_max

def _apply_action(self):
    # Option A: pure torque control (this guide)
    self.robot.set_joint_effort_target(self.torque_cmd, joint_ids=[0])

    # Option B: torque as FEEDFORWARD on top of the actuator PD (alternative)
    # self.robot.set_joint_position_target(theta_des, joint_ids=[0])
    # self.robot.set_joint_effort_target(self.torque_cmd, joint_ids=[0])

Two action-space architectures, pick one

Pure torque (Option A above). Policy outputs a torque directly. PD gains in the actuator cfg are typically set low or zero. Gives the policy maximum control authority but places the entire control burden on learning. Matches CST mode cleanly — what you're running on hardware.

Position target + torque feedforward (Option B). Policy outputs either a position target or a residual on top of a reference. The actuator's PD loop provides baseline tracking; the policy adds corrections. More stable to train, but the deployment-time PD gains must match exactly, and CST mode doesn't match this natively — you'd need CSP.

Since your real hardware runs CST (cyclic synchronous torque), Option A is the faithful choice. Train the way you'll deploy.

Action scaling gotcha

Action clamping to [-1, 1] happens in the env; action normalization (mean-std) is handled by RSL-RL automatically. Don't apply both, and don't let policy actions exceed ±1 without clamping — unclamped actions lead to numeric-instability blowups during training.

§ 11 — Reward shaping

Four terms for swing-up and balance.

The reward is where you express "what the policy should do." Four terms cover the pendulum swing-up task completely: uprightness, velocity penalty (don't just spin), action penalty (smooth control), and a sparse bonus for being close to vertical.

total reward per timestep $$ R = w_u \cdot r_{upright} + w_v \cdot r_{vel} + w_a \cdot r_{action} + w_b \cdot r_{bonus} $$
r_upright
cos(θ), in [-1, 1]. Maximum when θ = 0 (upright), minimum at ±π (hanging).
r_vel
−θ̇², penalizes spinning. Small weight.
r_action
−(action − prev_action)², penalizes jerky control.
r_bonus
+1 when cos(θ) > 0.95, else 0. Sparse reward pushes the policy to find the stable inverted equilibrium.
def _get_rewards(self) -> torch.Tensor:
    theta = self.robot.data.joint_pos[:, 0]
    theta_dot = self.robot.data.joint_vel[:, 0]
    action = self.prev_action.squeeze(-1)

    # uprightness: wrapped so θ=0 → +1, θ=±π → -1
    r_upright = torch.cos(theta)

    # penalize spinning
    r_vel = -theta_dot.pow(2)

    # penalize jerky control — difference from previous action
    if not hasattr(self, "_prev_action_for_reward"):
        self._prev_action_for_reward = torch.zeros_like(action)
    r_action = -(action - self._prev_action_for_reward).pow(2)
    self._prev_action_for_reward = action.clone()

    # sparse bonus near upright
    r_bonus = (r_upright > self.cfg.bonus_cos_threshold).float()

    total = (
        self.cfg.w_upright * r_upright
        + self.cfg.w_velocity_penalty * r_vel
        + self.cfg.w_action_penalty * r_action
        + self.cfg.w_bonus * r_bonus
    )
    return total

Tuning the weights

Start with the values in the env_cfg (w_upright=1.0, w_vel=0.01, w_action=0.001, w_bonus=5.0). Watch the training curves. Symptoms and fixes:

SymptomCauseFix
Policy spins forever at high speedvelocity penalty too smallincrease w_velocity_penalty to 0.02–0.05
Policy chatters torque at maxaction penalty too smallincrease w_action_penalty to 0.005–0.01
Policy swings up but doesn't holdbonus too small or threshold too tightincrease w_bonus, loosen threshold to 0.90
Policy does nothing (hangs down)reward landscape is flat near hangingadd a small reward for angular momentum during startup

Before worrying about sim-to-real, your policy must solve the task in sim. If mean episode reward doesn't rise above ~4 × w_upright within 500 iterations, your reward is the problem, not your PPO hyperparameters. Fix the reward first.

§ 12 — Terminations & resets

When to stop, how to restart.

Two termination conditions: timeout (fixed episode length) and optional early termination on catastrophic state. Reset logic randomizes initial conditions per episode — a big source of sample efficiency.

def _get_dones(self) -> tuple[torch.Tensor, torch.Tensor]:
    # termination: none (no catastrophic failure mode on a pendulum)
    terminated = torch.zeros(self.num_envs, dtype=torch.bool, device=self.device)

    # timeout: handled automatically by DirectRLEnv from episode_length_s
    time_out = self.episode_length_buf >= self.max_episode_length
    return terminated, time_out


def _reset_idx(self, env_ids: torch.Tensor | None):
    if env_ids is None:
        env_ids = self.robot._ALL_INDICES

    super()._reset_idx(env_ids)

    # Randomize initial θ across the full rotation — swing-up from anywhere
    theta_init = torch.empty(len(env_ids), device=self.device).uniform_(
        -math.pi, math.pi
    )
    theta_dot_init = torch.empty(len(env_ids), device=self.device).uniform_(
        -0.5, 0.5
    )

    joint_pos = torch.zeros((len(env_ids), 1), device=self.device)
    joint_pos[:, 0] = theta_init
    joint_vel = torch.zeros_like(joint_pos)
    joint_vel[:, 0] = theta_dot_init

    self.robot.write_joint_state_to_sim(joint_pos, joint_vel, env_ids=env_ids)

    # Domain randomization hook — params resampled here (§13)
    self._randomize_params(env_ids)

    # Reset bookkeeping
    self.prev_action[env_ids] = 0.0
    self._prev_action_for_reward[env_ids] = 0.0

Why random initial conditions matter

If every episode starts with the bar hanging straight down, the policy learns one specific swing-up trajectory. Starting from uniform random θ forces it to generalize to every starting pose. The 0.5 rad/s velocity noise does the same for initial velocities — prevents the policy from memorizing "at t=0, θ̇ is exactly zero."

Continuous rotation (your bench's capability) means you can also randomize starting from multiple rotations away from upright. Not needed for swing-up but useful later for other tasks.

Part IV

Sim-to-real hardening.

Three techniques that make the policy actually work on your bench. Skip any one and transfer quality drops noticeably.

§ 13 — Domain randomization

Randomize around identified values.

Every parameter you measured on the bench gets a ± range in simulation. The policy trains across the range, learning to tolerate variation it will actually encounter on real hardware. Ranges come from the motor-ID table, not guesses.

What to randomize, and how much

ParameterNominalRangeRationale
Payload mass1.0 kg[0.3, 2.0]Humanoid manipulates unknown objects
Payload COM0.30 m±0.05 mObject attachment variability
Coulomb friction F_c0.15 N·m±30%Temperature + lubrication drift
Viscous friction F_v0.05±30%Same sources
τ_sat (peak torque)60 N·m[50, 60]Thermal derating under sustained load
Kp22.95±10%Controller timing jitter, gain quantization
Kd2.14±10%Same

Implementation — randomize on episode reset

def _randomize_params(self, env_ids: torch.Tensor):
    n = len(env_ids)
    dev = self.device

    # sample per-env masses in kg
    payload_mass = torch.empty(n, device=dev).uniform_(0.3, 2.0)
    # bar_link mass = fixed bar + randomized payload
    mass_tensor = 0.3 + payload_mass                       # bar alone ≈ 0.3 kg

    # apply to articulation (affects physics next step)
    self.robot.root_physx_view.set_masses(
        mass_tensor.unsqueeze(-1).expand(-1, 2),  # [base, bar]
        env_ids,
    )

    # PD gains (one per env)
    kp = torch.empty(n, device=dev).uniform_(20.65, 25.25)     # ±10%
    kd = torch.empty(n, device=dev).uniform_(1.93, 2.35)
    self.robot.write_joint_stiffness_to_sim(kp.unsqueeze(-1), env_ids=env_ids)
    self.robot.write_joint_damping_to_sim(kd.unsqueeze(-1), env_ids=env_ids)

    # friction
    fc = torch.empty(n, device=dev).uniform_(0.105, 0.195)
    self.robot.write_joint_friction_to_sim(fc.unsqueeze(-1), env_ids=env_ids)

§ 14 — Latency injection

Real systems have delay. Simulate it.

On hardware, there's ~1–3 ms between encoder reading and torque application: EtherCAT transport + current loop rise time. Isaac's default sim has zero latency. A policy trained without latency learns high-frequency corrections that destabilize real hardware.

Two ways to inject latency

Option A — DelayedPDActuatorCfg. Replace DCMotorCfg with DelayedPDActuatorCfg, which buffers commanded efforts by N sim steps. Set min_delay and max_delay in steps; Isaac randomizes per env. Clean, but couples action delay to the actuator model.

Option B — buffer the action in the env. Keep a rolling queue in _pre_physics_step:

def _pre_physics_step(self, actions: torch.Tensor):
    # one-time init on first call
    if not hasattr(self, "action_buffer"):
        max_delay_steps = 3
        self.action_buffer = torch.zeros(
            (max_delay_steps + 1, self.num_envs, 1), device=self.device
        )
        # per-env random delay, in steps
        self.delay_steps = torch.randint(
            1, max_delay_steps + 1, (self.num_envs,), device=self.device
        )

    # roll and store
    self.action_buffer = torch.roll(self.action_buffer, shifts=1, dims=0)
    self.action_buffer[0] = actions

    # gather per-env delayed action
    idx = self.delay_steps.unsqueeze(-1)
    delayed_actions = self.action_buffer.gather(0, idx.unsqueeze(0).expand(1, -1, 1)).squeeze(0)

    # pass delayed_actions to the rest of the action pipeline
    self.prev_action = actions.clone()                     # policy sees its own undelayed action
    tau_max = self.cfg.robot_cfg.actuators["x6"].effort_limit
    self.torque_cmd = delayed_actions.clamp(-1.0, 1.0) * tau_max

At 200 Hz physics, 1–3 sim steps = 5–15 ms — covers the X6's EtherCAT + current-loop latency range.

Match the simulated latency to your measured real latency. Step 09 of the motor-ID protocol gives you the exact number for your EtherCAT stack. Put it here.
§ 15 — Observation normalization

Freeze it before ONNX export.

RSL-RL normalizes observations using running mean and standard deviation during training. The running statistics keep updating every batch. If you export to ONNX mid-training, the deployed policy sees observations normalized against a frozen snapshot of those stats — but the mean and std are themselves parameters that must be exported with the policy.

The failure mode

Train for 1000 iters with running normalization. Export the policy weights alone, not the normalizer. Deploy. The policy outputs garbage, because at deploy time your observations are fed through some other normalization (or none). The policy has effectively never seen the input distribution it's now getting.

The fix

RSL-RL's export wrapper handles this correctly if you use the provided export script (§19). Two things must be true at export:

  • Running stats are frozen — no more updates after the snapshot.
  • The ONNX export fuses the normalization layer into the model graph, so at deploy, raw observations go in and normalized actions come out. No separate normalizer process.

RSL-RL's OnnxPolicyExporter does both automatically. Use it. Don't try to roll your own export path without checking the normalization first — this is the single most common ONNX-deployment silent failure in the Isaac Lab ecosystem.

§ 16 — PPO hyperparameters

Sensible defaults, one joint.

FILE .../tasks/direct/pendulum_swingup/agents/rsl_rl_ppo_cfg.py 
from isaaclab.utils import configclass
from isaaclab_rl.rsl_rl import RslRlOnPolicyRunnerCfg, RslRlPpoActorCriticCfg, RslRlPpoAlgorithmCfg


@configclass
class PendulumSwingupPPORunnerCfg(RslRlOnPolicyRunnerCfg):
    num_steps_per_env = 24             # rollout buffer per env before PPO update
    max_iterations = 2000              # should converge well before this
    save_interval = 100
    experiment_name = "pendulum_swingup"
    empirical_normalization = True     # obs normalization on, frozen at export

    policy = RslRlPpoActorCriticCfg(
        init_noise_std=1.0,
        actor_hidden_dims=[128, 128],   # small task, small net
        critic_hidden_dims=[128, 128],
        activation="elu",
    )

    algorithm = RslRlPpoAlgorithmCfg(
        value_loss_coef=1.0,
        use_clipped_value_loss=True,
        clip_param=0.2,
        entropy_coef=0.005,            # light exploration bonus
        num_learning_epochs=5,
        num_mini_batches=4,
        learning_rate=1e-3,
        schedule="adaptive",              # auto-adjust LR based on KL divergence
        gamma=0.99,
        lam=0.95,                        # GAE lambda
        desired_kl=0.01,
        max_grad_norm=1.0,
    )

Sizing choices for single-joint

  • 128×128 hidden dims. Pendulum is a 2-DOF state problem (θ, θ̇). 128×128 is overkill but trains fine; going smaller (64×64) works too and trains faster.
  • 24 steps per env. At 4096 envs, that's ~100k samples per PPO update. Plenty of data per update; fewer means faster updates but higher variance.
  • learning_rate=1e-3, adaptive schedule. Adaptive LR auto-lowers when KL gets too large (prevents PPO from taking destructive steps). Safe default.
  • entropy_coef=0.005. Light; PPO's clip does most of the exploration work. Increase to 0.01 if the policy collapses too fast to deterministic behavior.
  • max_iterations=2000. Upper bound. Swing-up typically converges in 300–800 iterations at 4096 envs.

§ 18 — Validate before ONNX

Two quick checks that prevent wasted deployment time.

Before exporting and pushing to hardware, run two validation passes in sim. They take five minutes total and catch ~80% of issues that would otherwise appear on real hardware.

Validation 1 — play the policy in sim

# with a GUI so you can watch
./isaaclab.sh -p scripts/reinforcement_learning/rsl_rl/play.py \
    --task Isaac-PendulumSwingup-Direct-v0 \
    --num_envs 32 \
    --checkpoint logs/rsl_rl/pendulum_swingup/LATEST/model_500.pt \
    --real-time

Watch 32 envs. What should happen:

  • All 32 swing up within 2–3 seconds of episode start
  • Once upright, they stay upright with small corrections, not hunting wildly
  • Bar barely overshoots after reaching upright
  • Torque command looks smooth, not saturating constantly

If any of these fails, the policy isn't ready. Retrain with a fix (wider DR, tweaked reward, more iterations).

Validation 2 — sweep hard conditions

Re-run play with pessimistic parameter settings — the edges of your DR ranges:

§ 20 — Deploy through ros2_control

The last mile.

The ONNX runs in a ROS 2 node that subscribes to /joint_states, assembles the observation, runs inference at 50 Hz (matching training's policy rate), and publishes the scaled torque to the effort controller. Same code for Gazebo validation and real hardware — only the hardware interface underneath changes.

# ros2_ws/src/pendulum_policy/pendulum_policy/inference_node.py
import numpy as np
import onnxruntime as ort
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState
from std_msgs.msg import Float64MultiArray


class PendulumPolicyNode(Node):
    def __init__(self):
        super().__init__("pendulum_policy")
        self.sess = ort.InferenceSession("exports/pendulum_swingup_v1.onnx")
        self.input_name = self.sess.get_inputs()[0].name

        self.theta = 0.0
        self.theta_dot = 0.0
        self.prev_action = 0.0
        self.t_start = None

        # must match training values
        self.tau_max = 20.0
        self.vel_max = 16.0
        self.episode_length_s = 8.0

        self.create_subscription(JointState, "/joint_states", self.on_js, 10)
        self.pub = self.create_publisher(
            Float64MultiArray, "/effort_controllers/commands", 10
        )
        self.create_timer(1.0/50.0, self.tick)                     # 50 Hz = training rate

    def on_js(self, msg: JointState):
        if "pendulum_joint" in msg.name:
            i = msg.name.index("pendulum_joint")
            self.theta = float(msg.position[i])
            self.theta_dot = float(msg.velocity[i])

    def tick(self):
        if self.t_start is None:
            self.t_start = self.get_clock().now().nanoseconds / 1e9
        t = self.get_clock().now().nanoseconds / 1e9 - self.t_start
        t_frac = min(t / self.episode_length_s, 1.0)

        # assemble observation IN THE SAME ORDER as training
        theta_w = np.arctan2(np.sin(self.theta), np.cos(self.theta))
        obs = np.array([[
            np.cos(theta_w),
            np.sin(theta_w),
            self.theta_dot / self.vel_max,
            self.prev_action,
            t_frac,
        ]], dtype=np.float32)

        action = self.sess.run(None, {self.input_name: obs})[0][0, 0]
        action = float(np.clip(action, -1.0, 1.0))
        self.prev_action = action

        tau = action * self.tau_max
        msg = Float64MultiArray(data=[tau])
        self.pub.publish(msg)


def main():
    rclpy.init()
    rclpy.spin(PendulumPolicyNode())

Before pushing to real hardware: (1) this node runs cleanly in Gazebo with the simulated actuator from the Gazebo-actuator guide, (2) tracking looks qualitatively like the Isaac play session, (3) the ROS 2 bag shows the observation order matches training, (4) tau_max, vel_max, and episode_length_s constants match training values. All four? Deploy. Any one missing? Fix first.

The PVT deployment path

On the pendulum bench the pure-effort deployment above is now the alternative, not the default. The X6 drive boots into PVT (CiA-402 mode 5) and pendulum_pvt_controller claims position / velocity / effort / kp / kd command interfaces; the impedance law tau = Kp(q_d - q) + Kd(qd_d - qd) + tau_ff runs in drive firmware at 1 kHz. The policy node publishes a trajectory_msgs/JointTrajectoryPoint setpoint on ~/setpoint; the controller streams it to the drive every cycle. This mirrors Isaac Lab's ImplicitActuatorCfg — the same gain numbers used in ArticulationCfg apply unmodified.

# Step to 1.0 rad — controller flips into PVT on first setpoint
ros2 topic pub --once /pendulum_pvt_controller/setpoint \
  trajectory_msgs/msg/JointTrajectoryPoint \
  '{positions: [1.0], velocities: [0.0], accelerations: [0.0]}'

Around the controller, pendulum_safety_supervisor wraps both the effort and PVT paths with a latched e-stop and a thermal kp_scale derate, broadcast on two latched std_msgs topics (/pendulum/safety/estop_state, /pendulum/safety/kp_scale). See the safety supervisor field note and the PVT tuning field note for the full contract.

Use the pure-effort deployment when PVT mode isn't available (e.g. drives without firmware support, or a sim plugin that only exposes effort); use the PVT deployment when you want sim-to-real gain parity with Isaac's ImplicitActuator at the lowest possible jitter — the PD loop sits one EtherCAT cycle away from the encoder, not one host control cycle.

§ 22 — Three-task roadmap

From swing-up to the humanoid.

Swing-up is the first task. Two more build the skills you'll actually need on the humanoid — all on the same pendulum. Each task reuses the previous task's infrastructure, so only the env and reward change.

Task 1 · ~1 week
Swing-up and balance

What you just built. Validates the full pipeline: URDF → USD → env → PPO → ONNX → Gazebo → real. Success criterion: real hardware swings up in < 3 s from random initial position, holds upright with < 5° error for 10 s.

Task 2 · ~1 week
Trajectory tracking under disturbance

Command a reference θ(t) trajectory (sine wave, chirp, arbitrary path). Reward is −|θ − θ_d|². Randomize payload during episode (swap between 0.5 and 1 kg at random times). Success: real hardware tracks with RMSE < 0.05 rad across payload swaps without retraining. This is the humanoid-grade skill — handling changing load during motion.

Task 3 · ~1 week
Impact rejection

Hold upright; external disturbance torques applied at random times (simulated hits). Reward penalizes angular deviation + recovery time. Success: real hardware recovers to upright within 1 s after a manual push, without saturating torque. Tests the controller's disturbance rejection bandwidth — directly relevant to humanoid balance.

What you have at the end of three weeks

  • A validated Isaac Lab → Gazebo → real pipeline, proven end-to-end.
  • Three trained policies demonstrating position tracking, adaptive control, and disturbance rejection — the three humanoid-critical skills.
  • Measured sim-to-real transfer quality: RMSE numbers, success rates, failure modes.
  • Tuned DR ranges, tuned reward weights, tuned PPO hyperparameters — all at a scale where iteration costs minutes, not days.

When you scale up to the humanoid, the pipeline copies over unchanged. Only the URDF grows (25 joints instead of 1), the observation space expands, the action space expands, and the reward gets more terms. All the infrastructure you built on the pendulum — the actuator model, DR ranges, latency injection, normalization freezing, ONNX export path, ROS 2 inference node — transfers directly.

Every piece of Isaac Lab infrastructure you use on the pendulum is the same infrastructure you'll use on the humanoid. There's no "simple version for pendulum, real version for humanoid" — it's all one stack. Which means every debugging hour spent on the pendulum is an hour you don't spend debugging 25 coupled joints at once.

Train the pipeline first, train the policy second. The pipeline is the real product.
