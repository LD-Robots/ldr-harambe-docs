§ 01 — Why a separate package

Limits were scattered. Now they aren't.

Before this package each controller carried its own clamp_symmetric and tau_limit; DriveStatusBroadcaster knew temperature thresholds but only published /diagnostics and never acted; the policy node had an ad-hoc fall e-stop. Same numbers, three places, two of them dormant.

pendulum_safety makes them one library, one config file and one supervisor.

The package caps position, velocity, effort and temperature, and drives a configurable, manually-reset emergency stop shared by all three control paths (pendulum_pd_control, pendulum_pvt_control, pendulum_pvt_policy).

§ 02 — The two halves

One library linked into every controller. One supervisor node.

The package splits cleanly into a realtime-safe library that runs inside each controller process and a stand-alone supervisor that does breach detection and drives the e-stop.

§ 03 — The limiter library

Header-only and allocation-free, on the hot path.

A realtime-safe C++ library — every function reachable from a controller's update() is allocation-free, lock-free and log-free.

§ 04 — The supervisor node

A plain rclcpp::Node, a 200 Hz watchdog, a latched breach.

pendulum_safety_supervisor runs every breach predicate on the latest telemetry inside a watchdog timer (watchdog_rate_hz, default 200 Hz), latches the first breach, and drives the e-stop.

Services

# Manual e-stop — latches BreachReason::MANUAL immediately
ros2 service call /pendulum_safety_supervisor/estop std_srvs/srv/Trigger

# Manual reset — REFUSED (success=false) while any breach is still active
ros2 service call /pendulum_safety_supervisor/reset std_srvs/srv/Trigger

The latch never auto-clears — once tripped it stays tripped until ~/reset succeeds, and reset succeeds only when every predicate is back in range. This is deliberate: the drive cannot silently re-energise without an operator.

§ 05 — The e-stop signalling contract

Two latched std_msgs topics. No service round-trip.

The supervisor → controller link is two latched std_msgs topics — no custom messages. Controllers consume them via EstopSubscriber, which stores the values in lock-free atomics so update() reads them with no blocking.

  • /pendulum/safety/estop_state (Int8): 0 = clear, 1 = e-stop + FREE, 2 = e-stop + HOLD, 3 = e-stop + DAMPING.
  • /pendulum/safety/kp_scale (Float64): Kp is multiplied by this every cycle — 1.0 when cool or when no supervisor is running.
Reaction time < 10 ms — a controller reacts inside its own 1 kHz update(). The only latency is topic delivery plus one control cycle.

The latched topics have no publisher, the atomics keep their defaults (no e-stop, kp_scale = 1.0), and every control path behaves exactly as it did before this package existed. The dependency is opt-in by construction.

§ 06 — Per-trigger FREE / HOLD / DAMPING

Each breach picks its own reaction.

Each breach category resolves to an action — FREE (zero torque, the joint coasts), HOLD (lock at the position latched when the e-stop fired), or DAMPING (viscous brake — τ = −Kd_damp · qd, no position regulation; the joint decelerates and settles wherever it stops) — set in config/safety_limits.yaml:

    action.temperature: free        # over-temp / bus voltage
    action.overspeed: hold
    action.position: hold           # out-of-range position
    action.manual: free
    action.stale_joint_state: hold  # lost /joint_states
    action.sustained_effort: hold   # also: "damp" for a viscous brake

An e-stop HOLD or DAMPING overrides the controller's own FREE mode — safety must apply its chosen response regardless of what the operator asked for.

Only the PVT controller currently honours action: damp (via write_damping_outputs() using its Kd_damp parameter). The PD controller treats damp like hold — a damping path on the PD side hasn't been wired up yet.

§ 07 — Configuration

One source of truth — safety_limits.yaml.

config/safety_limits.yaml is the only place limit numbers are edited. Its /**: wildcard block means the same file applies to whatever node it is passed to — the supervisor, all three controllers (via an extra --param-file on the spawner) and the policy node all read the same safety.* values.

Every safety.* parameter is hot-reloaded. ros2 param set safety.position_min -1.0 takes effect on the supervisor's next 200 Hz watchdog tick and on the next update() cycle of every active controller — no relaunch. The catch: each node has its own parameter store, so a CLI param set on the supervisor doesn't fan out to the controllers (or vice versa). The pvt_tuner's Safety limits panel does that fan-out in one click.

Launching

ros2 launch pendulum_safety safety.launch.py             # real hardware
ros2 launch pendulum_safety safety.launch.py use_sim:=true   # simulation

safety.launch.py is also pulled in automatically by pvt.launch.py and pd_custom.launch.py (and, transitively, policy.launch.py) — so the supervisor comes up with the control stack and the controllers receive safety_limits.yaml on their spawners.

In simulation (use_sim:=true) there are no temperature interfaces, so the launch sets monitor_temperature:=false (the supervisor skips the temperature subscriptions and checks) and points the effort source at /joint_states. The supervisor still monitors position, velocity, sustained effort and joint-state freshness.

§ 09 — Caveats & extension points

What the clamp doesn't catch.

The clamp is a software layer, not the last line of defence. On real hardware the drive's 0x6072 max_torque SDO remains the independent hardware torque ceiling. clampEffort sits above it.
  • Temperature monitoring is real-hardware only. DriveStatusBroadcaster (the temperature source) does not run in Gazebo. In sim the supervisor runs with monitor_temperature:=false; thermal derating and over-temp e-stops are inactive there.
  • DriveStatusBroadcaster keeps its own thresholds. It still grades /diagnostics for reporting; its threshold numbers are intentionally kept in sync with safety_limits.yaml. The supervisor is the component that acts.
  • A NaN reading never latches an e-stop. Missing telemetry (an unread interface, a silent sensor) is treated as "no data", not as a breach.

Verifying

# supervisor up, initial state clear
ros2 topic echo --once /pendulum/safety/estop_state    # data: 0

# manual e-stop -> state 1, breach MANUAL
ros2 service call /pendulum_safety_supervisor/estop std_srvs/srv/Trigger
ros2 topic echo --once /pendulum/safety/breach_reason  # data: MANUAL

# overspeed: publish joint states past velocity_limit -> state latches, OVERSPEED
ros2 topic pub -r 50 /joint_states sensor_msgs/msg/JointState \
  "{name: [pendulum_joint], velocity: [100.0]}"

# reset is refused while the breach is still active, succeeds once back in range
ros2 service call /pendulum_safety_supervisor/reset std_srvs/srv/Trigger
