§ 01 — Why default Gazebo fails

An ideal torque source is not a motor.

Gazebo's default actuator, out of the box, is perfect. You command a torque, the joint experiences that torque, instantly, with zero friction, zero saturation, zero lag. Your policy trains against this and learns strategies that exploit an environment your real motor cannot provide. The gap looks something like this:

Torque response to a 5 N·m step command
ideal vs realistic actuator
The real motor (and a first-order lag model) rises to the commanded torque with a ~10 ms time constant. Gazebo's default is the flat amber line at 5 — no dynamics at all. A policy trained against the flat line has no experience of transient behavior, and over-commands when deployed.

A policy trained against a perfect world fails the first time reality disagrees with it. The job of the simulated actuator is to disagree the same way the real one does.
§ 02 — Architecture

Where does the actuator model live?

There's exactly one question to answer before you write any code: at which point in the pipeline do you modify the torque? There are three sensible answers — before the controller, after the controller, or inside the hardware interface — and they correspond directly to Options 2, 3, and "don't do this." The diagram:

The actuator model can sit in a wrapper node (Opt 2) or inside the hardware interface plugin (Opt 3). Opt 3 is structurally identical to the real-hardware interface — you swap one plugin for another at deployment. That's the architecture you want long-term.

The default path (top row) leaves the torque command unchanged all the way to Gazebo. Both Option 2 and Option 3 insert the actuator model; the only difference is where. Option 3's placement matters because it mirrors the structure of your real-hardware interface — so when you deploy, you're replacing one well-defined component, not rewiring the graph.

§ 03 — Option 1

URDF joint tags.

The laziest path — and sometimes the right one for bringup. Gazebo reads <dynamics damping> and <dynamics friction> from the joint and applies them inside its solver. Zero code. Use this for "does my launch file work" testing, not for policy validation.

<!-- inside your URDF, per joint -->
<joint name="pendulum_joint" type="continuous">
  <parent link="base_link"/>
  <child  link="bar_link"/>
  <axis xyz="0 0 1"/>

  <dynamics
     damping="0.05"     <!-- F_v, viscous -->
     friction="0.15"/>   <!-- Coulomb-ish threshold -->

  <limit effort="12.0" velocity="20.0"/>
</joint>

What you get

  • Viscous damping applied inside Gazebo's solver, mathematically clean.
  • Torque limit enforced at the joint level.
  • A "friction" parameter that's more like a velocity-gated resistance than true Coulomb friction — the implementation varies by Gazebo version and physics engine.

What you don't get

  • No first-order torque lag — instant response to every command.
  • No stiction, no asymmetric friction, no backlash.
  • No hook for domain randomization at runtime — parameters are baked into the URDF.
  • No shared structure with your real hardware interface, so you throw this away later.
Fine for the first 30 minutes. Use Option 1 to confirm your URDF loads, TF tree looks right, and the controller spawns. Then move to Option 2 the same day. Never train a policy with only Option 1 in the loop.
§ 04 — Option 2

A Python wrapper node before the controller.

The actuator model lives in its own ROS 2 node that sits between your policy and the effort controller. Policy publishes raw torque commands; wrapper consumes them, applies the model, republishes to the controller. Full implementation below — paste it into actuator_wrapper.py, adjust the topic names, launch it alongside your other nodes.

#!/usr/bin/env python3
"""
Actuator-model wrapper for Gazebo sim-to-real validation.

Subscribes:  /policy_effort_raw     (Float64MultiArray, N joints)
             /joint_states          (sensor_msgs/JointState)
Publishes:   /effort_controllers/commands  (Float64MultiArray)

Applies per joint:  saturation → first-order torque lag → friction.
Exposes params via ros2 param set for domain randomization.
"""

import numpy as np
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState
from std_msgs.msg import Float64MultiArray


class ActuatorWrapper(Node):

    def __init__(self):
        super().__init__('actuator_wrapper')

        # ── identified motor params — from §09 of the tuning guide ──
        self.declare_parameter('Fc',      0.15)    # Coulomb, N·m
        self.declare_parameter('Fv',      0.05)    # viscous, N·m·s/rad
        self.declare_parameter('tau_m',   0.010)   # motor lag, s
        self.declare_parameter('tau_max', 12.0)    # hard limit, N·m
        self.declare_parameter('rate_hz', 1000.0)
        self.declare_parameter('joint_name', 'pendulum_joint')

        # ── controller + model state ──────────────────────
        self.tau_applied = 0.0      # filtered torque (lag state)
        self.tau_cmd     = 0.0      # latest raw command from policy
        self.velocity    = 0.0      # latest measured joint velocity

        rate = self.get_parameter('rate_hz').value
        self.dt = 1.0 / rate

        # ── ROS I/O ───────────────────────────────────────
        self.create_subscription(
            Float64MultiArray, '/policy_effort_raw',
            self.on_policy_cmd, 10)
        self.create_subscription(
            JointState, '/joint_states',
            self.on_joint_state, 10)
        self.pub = self.create_publisher(
            Float64MultiArray, '/effort_controllers/commands', 10)

        self.create_timer(self.dt, self.tick)
        self.get_logger().info(f'ActuatorWrapper up at {rate:.0f} Hz')

    def on_policy_cmd(self, msg):
        if len(msg.data) > 0:
            self.tau_cmd = float(msg.data[0])

    def on_joint_state(self, msg):
        name = self.get_parameter('joint_name').value
        if name in msg.name:
            i = msg.name.index(name)
            self.velocity = msg.velocity[i]

    def tick(self):
        Fc      = self.get_parameter('Fc').value
        Fv      = self.get_parameter('Fv').value
        tau_m   = self.get_parameter('tau_m').value
        tau_max = self.get_parameter('tau_max').value

        # ── 1. saturate the raw policy command ──
        tau_c = np.clip(self.tau_cmd, -tau_max, tau_max)

        # ── 2. first-order torque lag ───────────
        alpha = self.dt / max(tau_m, 1e-6)
        self.tau_applied += (tau_c - self.tau_applied) * alpha

        # ── 3. friction (opposes motion) ────────
        # tanh replaces sign() to avoid chatter near zero
        tau_fric = Fc * np.tanh(self.velocity / 0.01) + Fv * self.velocity

        # ── 4. net torque published to Gazebo ───
        tau_net = self.tau_applied - tau_fric

        out = Float64MultiArray()
        out.data = [float(tau_net)]
        self.pub.publish(out)


def main():
    rclpy.init()
    rclpy.spin(ActuatorWrapper())


if __name__ == '__main__':
    main()

Why this works

  • Your policy outputs to /policy_effort_raw; the wrapper corrupts it with realistic effects and forwards to the controller. The effort controller is pass-through, so Gazebo receives τ_net.
  • All params are ROS 2 parameters. To randomize at training time, call ros2 param set from your training wrapper between episodes.
  • Uses rclpy timers at 1 kHz — matching the real control loop.
  • The same node runs during training and during Gazebo validation; you simply unplug it when deploying to real hardware, because the real motor has its own lag and friction.

Corresponding controller YAML

controller_manager:
  ros__parameters:
    update_rate: 1000
    effort_controllers:
      type: forward_command_controller/ForwardCommandController

effort_controllers:
  ros__parameters:
    joints: [pendulum_joint]
    interface_name: effort
Timing gotcha. The wrapper runs on its own timer, independent of the controller-manager tick. In heavy sim you can get missed cycles. If you see sim latency issues, either use a SingleThreadedExecutor with pinned CPU affinity, or move to Option 3 — where the model runs inside the write() callback and is guaranteed to execute every control tick.
§ 05 — Option 3

A custom hardware_interface plugin.

The architecturally correct answer. You write a SystemInterface plugin whose write() method applies the actuator model before forwarding to the Gazebo joint API. Your real-hardware X6 CAN interface is a sibling class with the same signature — swapping between sim and real is a URDF parameter change, nothing else.

Header — simulated_x6.hpp

// simulated_x6_hardware/include/simulated_x6/simulated_x6.hpp
#pragma once

#include <hardware_interface/system_interface.hpp>
#include <rclcpp/macros.hpp>

namespace simulated_x6 {

class SimulatedX6 : public hardware_interface::SystemInterface {
public:
  RCLCPP_SHARED_PTR_DEFINITIONS(SimulatedX6)

  CallbackReturn on_init(const hardware_interface::HardwareInfo & info) override;
  CallbackReturn on_activate(const rclcpp_lifecycle::State &) override;
  CallbackReturn on_deactivate(const rclcpp_lifecycle::State &) override;

  std::vector<hardware_interface::StateInterface>   export_state_interfaces() override;
  std::vector<hardware_interface::CommandInterface> export_command_interfaces() override;

  hardware_interface::return_type read (const rclcpp::Time &, const rclcpp::Duration &) override;
  hardware_interface::return_type write(const rclcpp::Time &, const rclcpp::Duration &) override;

private:
  // Identified actuator parameters (loaded from URDF <hardware> block)
  double Fc_{0.15}, Fv_{0.05}, tau_m_{0.010}, tau_max_{12.0};

  // Per-joint state
  std::vector<double> position_, velocity_, effort_;       // measured
  std::vector<double> commanded_effort_;                  // raw command in
  std::vector<double> tau_applied_;                       // lag filter state
};

}  // namespace simulated_x6

Core implementation — simulated_x6.cpp

hardware_interface::return_type SimulatedX6::write(
    const rclcpp::Time & /*now*/,
    const rclcpp::Duration & period)
{
  const double dt = period.seconds();

  for (size_t i = 0; i < commanded_effort_.size(); ++i) {

    // 1. Saturate raw policy command
    double tau_c = std::clamp(commanded_effort_[i], -tau_max_, tau_max_);

    // 2. First-order torque lag
    const double alpha = dt / std::max(tau_m_, 1e-6);
    tau_applied_[i] += (tau_c - tau_applied_[i]) * alpha;

    // 3. Friction (opposes motion; tanh replaces sign)
    const double v = velocity_[i];
    const double tau_fric = Fc_ * std::tanh(v / 0.01) + Fv_ * v;

    // 4. Net torque → forward to Gazebo via the gz_ros2_control bridge
    const double tau_net = tau_applied_[i] - tau_fric;
    effort_[i] = tau_net;  // effort_ exposed as state; bridge applies it
  }
  return hardware_interface::return_type::OK;
}

Register the plugin as a pluginlib export, then reference it from the URDF:

<ros2_control name="SimulatedX6System" type="system">
  <hardware>
    <plugin>simulated_x6/SimulatedX6</plugin>
    <param name="Fc">0.15</param>
    <param name="Fv">0.05</param>
    <param name="tau_m">0.010</param>
    <param name="tau_max">12.0</param>
  </hardware>
  <joint name="pendulum_joint">
    <command_interface name="effort"/>
    <state_interface name="position"/>
    <state_interface name="velocity"/>
    <state_interface name="effort"/>
  </joint>
</ros2_control>

Why this is the long-term answer

  • The model runs inside write(), guaranteed every control tick — no missed cycles.
  • Identical interface surface to your real-hardware plugin (RealX6CAN). Deployment is a URDF edit.
  • Parameters can be set at runtime via services or the ros2_control parameter interface — domain randomization just works.
  • The same plugin can wrap MuJoCo, Isaac, Gazebo, or real hardware. Swap the transport layer, keep the actuator model.

A bit more upfront work: CMakeLists, plugin description XML, pluginlib registration. Budget a day. After that it's a permanent asset for the humanoid project.

§ 06 — Option 4

Use MuJoCo, keep the same ros2_control contract.

A serious alternative worth considering on the single-joint stage: run mujoco_ros2_control instead of gz_ros2_control. The ROS 2 side looks identical — same controllers, same YAML, same URDF block — but the underlying simulator has built-in actuator models that are much closer to reality than anything you'll roll by hand in Gazebo.

MuJoCo's actuator primitives

MuJoCo lets you attach an actuator to a joint and parameterize it with gainprm, biasprm, forcerange, and filter time constants. The motor actuator type models a first-order torque source natively — no custom code required:

<actuator>
  <motor name="pendulum_motor"
         joint="pendulum_joint"
         ctrlrange="-12 12"
         forcerange="-12 12"
         dyntype="filter" dynprm="0.010"/>  <!-- 10 ms lag -->
</actuator>

<default>
  <joint damping="0.05" frictionloss="0.15"/>  <!-- F_v, F_c -->
</default>

Trade-offs

For a single-joint policy validation, MuJoCo is arguably a better choice than Gazebo. For a full humanoid with cameras, contact sensors, and ecosystem tooling, Gazebo still wins. You can run both on the same ros2_control controllers — the decision is per-project, not per-robot.
§ 07 — Domain randomization inside sim

Re-sample parameters every episode.

The whole point of having a parameterized actuator model is that you can randomize it during training. On each episode reset, sample new values of Fc, Fv, τ_m, J (via link mass), and tau_max. The policy then learns to tolerate the real-world variation you measured in §09 of the tuning guide — not guesses, measurements-with-noise.

Sampling distribution

How to apply per episode (ROS 2 param approach)

# Called at the start of each training episode
def randomize_actuator(param_client, rng):
    params = {
        'Fc':      rng.uniform(0.105, 0.195),   # ±30% of 0.15
        'Fv':      rng.uniform(0.035, 0.065),
        'tau_m':   rng.uniform(0.005, 0.020),
        'tau_max': rng.uniform(10.0,  12.0),
    }
    set_parameters_atomically(param_client, params)

Use rclpy.parameter_client.AsyncParameterClient so the call doesn't block the episode reset loop. If you're using Option 3 (hardware interface plugin), expose the same parameters through the controller-manager parameter interface — same function signature, different client.

§ 08 — Validating sim matches real

The one test you must run before trusting the pipeline.

You have a sim actuator with your identified parameters. Before training any policy against it, verify it reproduces real-world behavior. Run the same trajectory on real hardware and in Gazebo with your model active, overlay the traces, compute RMSE. If they diverge by more than ~10%, fix the model — not the policy.

  • Pick a test trajectory A smooth quintic sweep from 0 to 0.5 rad in 1 second, returning to 0 in another 1 second. Wide enough to excite friction, fast enough to excite lag.
  • Record the real trace Run the trajectory on the X6 with your current PD + feedforward. Log /joint_states (θ, θ̇) at 1 kHz into a ros2 bag.
  • Record the sim trace Same trajectory, same PD gains, same feedforward, same launch file — but with the gz_ros2_control and actuator-wrapper nodes instead of the hardware driver.
  • Overlay and compute RMSE Plot θ(t) real vs θ(t) sim on the same axes. Compute RMSE over the trajectory window. If < 5%, model is excellent. 5–10%, acceptable. > 10%, debug.
  • Common divergence modes and fixes If sim leads real by a constant time offset → you missed the motor lag. If sim tracks tighter at low speed → you missed Coulomb friction. If sim tracks tighter at high speed → F_v is wrong. If sim has zero steady-state error and real has a bias → gravity feedforward isn't identical between the two.

Start with Option 2 this week. Get a baseline policy transferring from Isaac → Gazebo (via wrapper) → real in the pendulum test rig. Measure the real-vs-sim RMSE before and after the wrapper. That number — how much the actuator model closes the sim-to-real gap on a single joint — is the most important number in the project.
