Part I

The architecture.

What we're building, how the pieces connect, and why it stays this simple.

§ 01 — The setup at a glance

Two repos, one session, zero coupling.

The whole system rests on one Claude Code feature: additionalDirectories. One session operates across multiple folders without merging them into a monorepo. The robot repo remains the primary workspace; the docs repo is a loaded sibling that Claude can read and edit freely.

The workspace file is optional VS Code sugar; the actual Claude-Code wiring is additionalDirectories in robot/.claude/settings.json. That single setting makes docs/ visible in every session.

What this gives you

No context switching
1 window

Open VS Code on the workspace file, work across both repos without alt-tabbing.

No git coupling
0 submodules

Each repo has its own history. Commit docs when docs change, commit code when code changes.

Docs stay alive
Auto-sync

CLAUDE.md rules + one slash command keep docs in sync with real project state.

§ 02 — Directory layout

Sibling repos, one parent folder.

The layout is deliberately shallow. A non-git parent directory holds both repos as siblings. The parent exists only to own the VS Code workspace file — nothing else lives there.

On absolute paths. Throughout this guide I use ~/humanoid/ as the example root. Replace with your actual path (e.g., ~/code/humanoid/ or ~/projects/robotics/humanoid/) everywhere. Claude Code needs absolute paths in additionalDirectories — relative paths don't work reliably across session restarts.
§ 03 — Prerequisites

What you need installed.

  • Claude Code CLI Installed globally via npm: npm install -g @anthropic-ai/claude-code. Verify with claude --version. You need an active Anthropic API key or a Claude Pro/Max subscription — set ANTHROPIC_API_KEY in your shell profile if using API auth.
  • VS Code Any recent version. The stable channel is fine.
  • Git Already required for your robot repo. Nothing new.
  • A shell that supports absolute path expansion Bash, Zsh, Fish — all work. On Ubuntu: nothing to install.

VS Code extensions are covered in §12 — install them after the file setup is done, so everything works correctly on first open.

§ 04 — Initialize the docs repo

Create it, structure it, first commit.

From scratch, in the terminal. If you already have existing documentation, copy it in after step 2 and skip ahead.

mkdir -p ~/humanoid/docs

# 2. initialize git

# 3. create the directory structure

§ 05 — Docs repo CLAUDE.md

The docs repo's memory.

Every Claude Code session loads this file automatically when the repo is in scope. Keep it under ~150 lines — every low-value line weakens the high-value ones. Focus on conventions that matter to every documentation session.

FILE ~/humanoid/docs/CLAUDE.md 
# Humanoid project — documentation repository

## Purpose
Evolving technical documentation for the humanoid robot bring-up:
PD tuning, motor ID, sim-to-real strategy, Gazebo/Isaac integration,
hardware notes. Docs are living — they grow and mutate with the project.

## Design system
All HTML docs use the "Field Notes" design system defined in
`design_guide.md` at the repo root. Before creating or editing any HTML:

1. Read `design_guide.md` to pick up the CSS tokens, component patterns,
   and complete CSS block at the end of the file.
2. Use the components defined there — panels, callouts, cards, steps,
   bullets, math-block, tables — don't invent parallel ones.
3. When in doubt, match the tone and structure of an existing doc in
   the same subdirectory.

## Directory conventions
- `tuning/`    — identification procedures, per-joint tuning reports
- `strategy/`  — pipeline/architecture docs, decision records
- `hardware/`  — motor specs, wiring, mechanical notes
- Filenames follow `topic_verb_guide.html` (e.g., `pd_tuning_guide.html`)
  or `topic_report.html` for one-off reports.

## Writing voice
- Direct. Acknowledge what's already been done.
- Honest assessment over flattery.
- Concrete over abstract — use real measured numbers when available.
- No preamble, no "great question" openings.
- Prefer prose and short paragraphs over deep bullet nesting.

## Project state (update when this changes)
- Stage: single-joint bench (X6 motor, 70 cm bar, 1 kg @ 30 cm)
- Identified params: J ≈ 0.102 kg·m², mgl = 2.943 N·m,
  F_c ≈ 0.15 N·m, F_v ≈ 0.05 N·m·s/rad, τ_m ≈ 10 ms
- Stack: ROS 2 (effort control), Isaac Gym training, Gazebo validation
- End goal: ONNX policies transferring to full humanoid

## When editing existing docs
- Preserve `§ NN` section numbers. If inserting a section, renumber all
  following ones and update the TOC.
- Keep chart data inline (in the same HTML file) — don't split into
  separate JS files.
- Update the hero's "Status" meta row when project state changes.
- If the change is significant, add an entry to `CHANGELOG.md`.

## Git discipline
- Commit docs separately from code changes.
- Prefix commit messages with `docs:` when committing here.
- One logical change per commit.

Why these specific sections

  • Purpose — tells Claude what this repo is for in one paragraph. Prevents generic "I'll help you write documentation" responses.
  • Design system — points explicitly at design_guide.md. This is the single highest-leverage instruction.
  • Directory conventions — prevents docs from landing in the wrong folder.
  • Writing voice — shapes tone without you having to re-prompt every time.
  • Project state — gives Claude current values without a separate lookup. Update this section as the project evolves.
  • When editing existing docs — the operational rules that prevent the two most common failure modes (mangled section numbering, silent changelog drift).

§ 07 — The write-field-note skill

One skill, infinite docs.

A skill is a markdown file in .claude/skills/ with YAML frontmatter. When its trigger phrase matches (or you invoke it as /write-field-note), Claude loads it as a sub-prompt and follows its instructions. This one skill encapsulates the whole design system so every new doc inherits it without re-explanation.

FILE ~/humanoid/docs/.claude/skills/write-field-note.md 
---
name: write-field-note
description: Create a new technical documentation HTML file in the Field
  Notes design system. Trigger when the user asks to create a new guide,
  doc, reference, report, or write-up on a topic.
---

# Writing a field note

When creating a new technical doc, follow this procedure precisely.

## 1. Read the design system first
Before writing any HTML, read `design_guide.md` at the docs repo root.
Use its CSS tokens, component patterns, and the complete CSS block at the
bottom of that file verbatim. Do not invent new styling, new tokens, or
alternative layouts.

## 2. Determine the filename and location
Based on the topic, pick the right subdirectory:

- `tuning/`   — motor identification, PD tuning, per-joint reports
- `strategy/` — pipeline, architecture, decision records, planning
- `hardware/` — motor specs, wiring, mechanical, sensor calibration

Filename: `topic_verb_guide.html` or `topic_report.html`. Examples:
- `tuning/shoulder_pd_tuning_guide.html`
- `strategy/deployment_pipeline_guide.html`
- `hardware/ethercat_master_setup_guide.html`

If the topic doesn't fit existing directories, ask before creating a new one.

## 3. Required structure
Every doc has:

1. `<header class="hero">` with:
   - Eyebrow text (mono, tracked, amber)
   - H1 title with italic Fraunces + one amber emphasis word
   - Subtitle in Fraunces light
   - 4-item meta row (Status, Target, Stack, or similar)
   - Table of contents

2. Numbered sections `<section id="...">` each with:
   - `<span class="section-num">§ NN — short descriptor</span>`
   - H2 with italic amber `<em>` on one emphasis word
   - Optional `<p class="lead">` first paragraph

3. At least one of each high-impact component:
   - `<div class="callout">` — the thesis line in Fraunces italic
   - `<div class="panel" data-label="...">` — a key insight or rules list
   - `<table class="ref">` — tabular reference if applicable

4. Footer with doc identification and date.

## 4. Part dividers (for docs with 10+ sections)
If the doc has more than ~10 sections, group them into Parts using the
`.part` structure from the design guide. Parts have big Fraunces italic
headings and a brief pdesc descriptor.

## 5. Charts (if applicable)
- Use Chart.js loaded from jsDelivr CDN.
- Primary series color: `#e8a33d` (amber).
- Secondary: `#5fb3b3` (cyan).
- Warning/wrong: `#d97757` (rose).
- Grid: `#1e1a13`. Ticks/labels: `#a79a82`.
- Always include units in axis titles: `time [s]`, `torque [N·m]`.
- Legend at bottom, mono font.

## 6. Math (if applicable)
- Load KaTeX from jsDelivr CDN (see design_guide.md for exact snippet).
- Wrap display math in `<div class="math-block labeled">` with a
  `<span class="lbl">` caption above it.
- Follow every math block with a `<dl class="vars">` variable legend
  OR prose that uses the symbols.

## 7. After creating the file
1. Add a link from `README.md` under the appropriate section.
2. Add an entry to `CHANGELOG.md` if it exists.
3. Show the user the final file and summarize what's inside.
4. Offer to open it: `xdg-open <path>` on Linux.

## Checklist before marking done
- [ ] design_guide.md was read before writing.
- [ ] Filename matches the pattern.
- [ ] File is in the correct subdirectory.
- [ ] Hero, numbered sections, at least one callout/panel/table present.
- [ ] Chart colors and font are from the palette.
- [ ] README.md updated with a link.
- [ ] No invented CSS classes.

This skill is the workhorse. Every time you ask for a new doc — "write me a guide on EtherCAT master config" — Claude follows this procedure. Style drift becomes almost impossible.

§ 08 — Robot repo CLAUDE.md

Teach it where the docs live.

The robot repo probably already has a CLAUDE.md — or should. If it doesn't, run /init inside Claude Code from the repo root and let it scaffold one. Then add (or adapt) the section below that makes the docs repo a first-class citizen of every robot-repo session.

FILE ~/humanoid/robot/CLAUDE.md (add/merge these sections) 
# Humanoid robot — code repository

## Stack
- ROS 2 (Jazzy), ros2_control with effort interface
- Isaac Gym for RL training, Gazebo for validation
- Python for training scripts, C++ for hardware interfaces
- Policies deployed as ONNX through a minimal inference node

## Commands
- `colcon build --symlink-install` — build the workspace
- `. install/setup.bash` — source the env
- `ros2 launch humanoid_bringup pendulum.launch.py` — bring up pendulum
- `pytest tests/` — run Python tests

## Related documentation
Documentation lives in `~/humanoid/docs/` and is loaded into every
Claude Code session via `additionalDirectories` (see .claude/settings.json).

The docs repo follows the Field Notes design system defined in
`docs/design_guide.md`. When creating or editing any HTML there, use the
patterns, components, and CSS from that file — never invent new styling.

## When to update the docs

Update docs when ANY of these happen:
- Motor parameters change (mass, inertia, friction, torque limits)
  → `docs/tuning/motor_id_report.html` or relevant per-joint doc
- PD gains or controller config change
  → `docs/tuning/pd_tuning_guide.html`
- Sim-to-real pipeline architecture changes (new controller, new
  actuator model, new validation step)
  → `docs/strategy/sim_to_real_guide.html`
- You identify a new motor, joint, or a bug worth capturing
  → create a new field note via the `write-field-note` skill

Do NOT update docs for:
- Trivial refactors (renaming, formatting, comment tweaks)
- Experimental code on a feature branch that might not land
- WIP changes that aren't committed yet

## Doc update protocol
1. Read the existing doc first. Match its tone and structure.
2. Preserve `§ NN` section numbering. Renumber if inserting.
3. Keep changes surgical — modify only what changed, not the surrounding prose.
4. Commit docs in a SEPARATE commit with prefix `docs: `.

## Writing voice (applies to both code comments and doc edits)
- Direct. No preamble.
- Honest assessment over flattery.
- Concrete over abstract. Use real measured numbers.
The "When to update the docs" section is the most important part. It gives Claude an explicit trigger list, preventing both over-updating (docs churn from every trivial change) and under-updating (important facts silently drift out of sync).
§ 09 — Robot repo settings.json

The one setting that wires everything together.

This is the centerpiece of the setup. The additionalDirectories array lists absolute paths that every Claude Code session in this repo should treat as part of its workspace. Add the docs repo path, and docs become accessible without any manual /add-dir command.

FILE ~/humanoid/robot/.claude/settings.json 
{
  "additionalDirectories": [
    "/home/YOUR_USERNAME/humanoid/docs"
  ],
  "permissions": {
    "allow": [
      "Read(**)",
      "Read(/home/YOUR_USERNAME/humanoid/docs/**)",
      "Edit(/home/YOUR_USERNAME/humanoid/docs/**/*.md)",
      "Edit(/home/YOUR_USERNAME/humanoid/docs/**/*.html)",
      "Edit(/home/YOUR_USERNAME/humanoid/docs/**/*.yaml)",
      "Edit(**/*.py)",
      "Edit(**/*.cpp)",
      "Edit(**/*.hpp)",
      "Edit(**/*.yaml)",
      "Edit(**/*.xml)",
      "Edit(**/*.xacro)",
      "Edit(**/*.urdf)",
      "Edit(**/*.md)",
      "Bash(colcon build*)",
      "Bash(ros2 *)",
      "Bash(git status)",
      "Bash(git diff*)",
      "Bash(git log*)",
      "Bash(git add*)",
      "Bash(git commit*)",
      "Bash(git -C /home/YOUR_USERNAME/humanoid/docs *)",
      "Bash(ls*)",
      "Bash(cat*)",
      "Bash(pytest*)"
    ],
    "deny": [
      "Read(./.env*)",
      "Read(./secrets/**)",
      "Edit(./.git/**)"
    ]
  }
}
Replace YOUR_USERNAME. Claude Code resolves ~ differently across contexts; absolute paths are safest here. Find your actual path with echo $HOME and substitute. On most Ubuntu systems it's /home/yourname/.

What the key permissions do

  • additionalDirectories — makes the docs repo visible to the session. This is the core wiring.
  • Edit(...docs/**/*.md) and Edit(...docs/**/*.html) — explicit edit permission on the docs repo files. Without these, Claude would ask for confirmation on every doc edit.
  • Bash(git -C ...docs *) — lets Claude run git commands inside the docs repo using -C (change directory). This is how it commits doc changes from a session rooted in the robot repo.

§ 10 — The /sync-docs slash command

One command, end-of-session sync.

A slash command is a markdown file in .claude/commands/. When you type /sync-docs in the Claude Code REPL, it runs this prompt as if you'd pasted it. Good for scripted workflows you run repeatedly.

FILE ~/humanoid/robot/.claude/commands/sync-docs.md 
---
description: Review recent robot-repo changes and propose doc updates
  in ~/humanoid/docs/. Interactive — shows diffs before applying.
---

# Sync docs with recent work

Walk through this procedure to propagate recent robot-repo changes
into the docs repo. Show proposed changes as diffs, wait for
approval before applying.

## Step 1 — Gather context
Run these in parallel:
- `git log --oneline -30` in this repo (robot)
- `git -C /home/YOUR_USERNAME/humanoid/docs log -1 --format='%ai %s'`
  to find the last docs commit
- `git log --since="<last docs commit date>" --name-only` in this repo
  to see which files have changed since docs were last updated

## Step 2 — Identify documentation-relevant changes
For each changed file, decide if it warrants a doc update per the rules
in CLAUDE.md ("When to update the docs" section):

- Motor parameter change? → tuning/motor_id_report.html
- PD gain change?         → tuning/pd_tuning_guide.html
- Pipeline change?        → strategy/sim_to_real_guide.html
- New concept/procedure?  → consider a new field note

Ignore: refactors, formatting, WIP branches, test-only changes.

## Step 3 — Propose specific updates
For each doc that needs changing, show me:
1. The doc name and section that would change
2. A diff of the proposed edit (BEFORE and AFTER)
3. A one-line commit message

Wait for my "yes / skip / modify" on each one. Do not apply anything
automatically.

## Step 4 — Apply approved changes
After I approve all (or a subset):
1. Apply the edits to the docs repo.
2. For each doc, stage and commit in the docs repo:
   `git -C ~/humanoid/docs add <file>`
   `git -C ~/humanoid/docs commit -m "docs: <message>"`
3. Report the commit hashes.
4. Do NOT push. Remind me to push manually when ready.

## Step 5 — Summary
Give me a short summary:
- N docs updated
- M new field notes created (if any)
- Pending things you noticed but didn't change (e.g., stale claims
  you spotted but aren't sure if they should update)

Run this at the end of a work session — or whenever you sense the docs have drifted. It compares the last docs commit timestamp with robot-repo activity since then, and proposes targeted updates without you having to list them.

§ 13 — A day in the life

Three typical workflows, walked through.

Scenario 1 — Small change, direct update

You just re-identified the shoulder motor: F_c is now 0.17 N·m instead of 0.15.

# already in VS Code, workspace open, robot repo is the active terminal
claude

> I just re-identified the shoulder motor. F_c is now 0.17 N·m
  (was 0.15). Update the docs to reflect this and commit in the docs repo.

Claude reads the relevant docs (motor_id_report.html, pd_tuning_guide.html), finds every table or prose mention of F_c = 0.15, proposes a diff showing each change, you approve, it applies and commits in the docs repo with a clean message like docs: update shoulder F_c after re-identification.

Scenario 2 — New topic, create a field note

You got EtherCAT master config working and want to capture the procedure before you forget.

> Write a new field note on the EtherCAT master config I just set up.
  Cover: ethercat_conf.xml location, slave enumeration, scan timing,
  the two gotchas we hit (kernel preempt-rt, link aggregation).

The write-field-note skill triggers automatically. Claude reads design_guide.md, creates docs/hardware/ethercat_master_setup_guide.html in the right style, adds the link to docs/README.md, commits to the docs repo. Three files touched, you approve once.

Scenario 3 — End of day sync

Bunch of changes accumulated, not sure what's doc-worthy.

> /sync-docs

Claude compares the last docs commit to recent robot-repo activity, goes file by file through what changed, proposes specific doc updates for each one, you say yes/skip/modify. Takes ~2 minutes. At the end, docs repo has 3–5 fresh commits, each focused and well-labeled.

The key insight: you're never writing "remember to look at the docs repo" — it's always there. You describe what changed; Claude figures out where it should go.
§ 14 — Evolving the system

Add skills when you notice a pattern.

The initial setup is the minimum. Over weeks, you'll notice yourself re-explaining the same thing to Claude Code multiple times. That's the signal — turn it into a skill or a CLAUDE.md rule.

When to add a new skill

  • You've asked for the same kind of artifact three times with similar prompts (e.g., "write a per-joint tuning report" → codify as joint-tuning-report skill).
  • A workflow has multiple clear steps that Claude sometimes skips or reorders (e.g., re-identification → update params YAML → update docs → regenerate charts).
  • An output format is fiddly and Claude only gets it right if you remind it (e.g., "make sure the YAML keys are sorted alphabetically for diff-friendliness").

When to update CLAUDE.md

  • Project state changed — new stage reached, new stack piece added, new convention adopted.
  • You keep reminding Claude of the same preference ("I like prose over bullets"). Promote it to CLAUDE.md.
  • A new directory appeared and Claude is putting files in the wrong one.

When NOT to add more

  • You had one friction-y session and want to prevent it forever. Wait for a second occurrence — one-off issues don't earn permanent rules.
  • CLAUDE.md is approaching 200 lines. Instruction degradation is real — every low-value line weakens high-value ones. Promote stale rules to skills (which load on demand) or delete them.
  • The rule is "do what's obvious." Claude mostly gets defaults right; only codify when defaults fail.

Suggested second-wave skills (add when needed)

SkillTriggerDoes what
update-params"updated the params"Takes new identified values, updates the params YAML, propagates to every doc that references them, regenerates any derived charts.
add-joint"new joint added"Scaffolds per-joint doc + URDF snippet + controller YAML entry. Copies the pattern from an existing joint.
changelog-entry"log today's work"Appends a dated entry to CHANGELOG.md summarizing what changed in docs + robot this day.
release-report"tag a milestone"Generates a Field Notes HTML summarizing progress since the last tagged milestone.

Review the system every ~4 weeks. Read your CLAUDE.md files and ask: is each line still earning its place? Delete anything stale. Run /status in Claude Code occasionally to see which config sources are active and where they conflict.

§ 16 — Troubleshooting

When something doesn't work.

"Claude doesn't see the docs repo"

  • Check that additionalDirectories is a valid JSON array of absolute paths (no ~, no relative paths).
  • Run /status in Claude Code — it lists all active config sources and their origins. The additionalDirectories should show up under the project settings.
  • Restart the Claude Code session. Settings reload on session start, not mid-session.
  • Verify the path exists: ls /home/YOUR_USERNAME/humanoid/docs.

"Claude keeps asking permission for doc edits"

  • Your permissions.allow patterns must match the absolute paths, not the relative paths. Use Edit(/home/you/humanoid/docs/**/*.md), not Edit(docs/**/*.md).
  • Patterns are case-sensitive.
  • Verify with /status — it shows the effective permission set.

"Docs are losing style consistency over time"

  • The write-field-note skill isn't triggering. Check that Claude is actually reading design_guide.md before creating docs — you can ask directly: "Did you read design_guide.md first?"
  • If the skill's description field is too narrow, Claude won't invoke it. Broaden the description to include more trigger phrases.
  • Invoke explicitly: /write-field-note.

"CLAUDE.md feels too long"

  • 200 lines is the soft ceiling. Past that, instruction compliance degrades.
  • Promote detailed rules into skill files (loaded on demand) rather than CLAUDE.md (loaded always).
  • Delete anything that hasn't mattered in the last month.

"Git commits are ending up in the wrong repo"

  • Remind Claude via CLAUDE.md: use git -C /absolute/path/to/docs when committing docs; plain git only for the current repo.
  • Check git log in both repos after a session to confirm commits landed where you expected.

"VS Code multi-root workspace feels weird"

  • Each folder has its own settings, tasks, and launch configs. The workspace file can override these globally.
  • Terminal "starts in" the most-recently-active folder. Click into a specific folder before opening a new terminal to control which repo's CLAUDE.md loads.
  • You can close the workspace and open either repo individually if you need focus — the setup still works, you just lose the two-pane view.
When something breaks, /status inside Claude Code is your first diagnostic. It shows which CLAUDE.md files loaded, which settings files are active, and any parsing errors.
